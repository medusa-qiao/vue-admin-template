# 静态路由、动态路由与后端交接

本指南是新增业务的路由规范，源码路径相对当前正在开发的项目根。**先按最终授权来源分类，再实现 UI；纯前端开发不改变业务路由的动态属性。** 下文 `src/router/dynamic/` 与交接清单是首次新增业务时创建的文件约定，当前轻量模板仍只有基础页面和空动态菜单，没有数据库或账号状态服务。

## 1. 每个页面先填路由清单

| 必填项     | 内容                                                                        |
| ---------- | --------------------------------------------------------------------------- |
| 页面与标识 | 页面文件、URL、唯一 `name`、父目录、locale key                              |
| 来源       | `static` 或 `dynamic`，并写出分类理由                                       |
| 后端交接   | 是否需要入库、菜单/页面资源标识、组件 key、权限码；未确认字段标记待确认     |
| 访问条件   | 登录要求、允许角色、账号状态条件及其可信数据来源                            |
| UI 行为    | 菜单是否可见、详情页高亮、缓存、按钮权限来源、无权限/加载中/失败/无数据状态 |
| 验收       | 允许与拒绝账号、直接打开 URL、刷新、退出/切换账号、接口失败                 |

不能以“目前只有一个账号”“暂时没有后端”“菜单先写死方便调 UI”为理由把业务页归为静态。

| 类别                                          | 路由来源                                                     | 数据库存储                                               |
| --------------------------------------------- | ------------------------------------------------------------ | -------------------------------------------------------- |
| 固定首页及布局、登录、403/404/500、刷新重定向 | 静态基础路由，沿用现有文件                                   | 不加入业务菜单种子；公开访问仍由登录白名单单独决定       |
| 订单、用户、报表、业务配置等页面及目录        | 动态，按当前会话返回授权记录                                 | 交付菜单/页面资源及授权关联的种子或迁移清单              |
| 隐藏详情、编辑、全屏业务页面                  | 动态，与对应业务共同授权；`showLink: false` 只管展示         | 仍是受控页面资源，不能因无菜单而遗漏                     |
| 新增独立流程页                                | 先确认是否属于全局认证基础设施；只有明确的基础设施例外才静态 | 账号相关业务流程默认动态，后端契约待确认时不自行扩充例外 |

这里的基础首页指现有固定首页。若新增首页子页或业务看板按账号授权，它仍是动态业务资源。基础路由使用静态文件不表示免登录或免接口鉴权。从其他项目借鉴静态业务示例时，按本规范改为动态定义；改造已有业务时显式迁移对应模块。

## 2. 两类文件分开，分别经过一个入口

```text
src/router/
├── modules/                  # 已有静态发现目录，只新增基础路由
│   ├── home.ts
│   └── remaining.ts          # 登录、错误、刷新等基础设施
├── dynamic/                  # 新业务的可序列化定义，不放进 modules/
│   ├── types.ts              # DynamicRouteDto，与运行时 RouteRecordRaw 分开
│   ├── modules/orders.ts     # 订单目录、列表、隐藏详情
│   └── index.ts              # 按领域显式导入并汇总一次，作为开发目录/种子来源
├── index.ts                  # 现有静态入口和守卫
└── utils.ts                  # 现有动态初始化、组件映射与重置
src/api/routes.ts             # 始终通过 HTTP 获取当前会话的动态路由
mock/                        # 开发端点导入 dynamic/index.ts，模拟授权后返回
docs/backend/route-manifest.md # 新业务的后端交接清单，不是已执行的数据库迁移
```

静态入口已经使用 `./modules/**/*.ts` eager glob，并单独导入 `remaining.ts`。**不要将动态定义、类型、种子或二次汇总文件放到这个 glob 目录内**，也不要同时手工 import 再注册已被 glob 发现的模块。

动态定义的最小 DTO 示例（新增 `src/router/dynamic/types.ts`，按已确认契约扩展）：

```ts
export interface DynamicRouteDto {
  name: string;
  path: string;
  redirect?: string;
  component?: string;
  meta: {
    title: string;
    rank?: number;
    roles?: string[];
    auths?: string[];
    showLink?: boolean;
    activePath?: string;
    keepAlive?: boolean;
    icon?: string;
  };
  children?: DynamicRouteDto[];
}
```

`component` 保存例如 `orders/list/index` 的本地视图 key，`title` 保存 `menus.orderList` 的 locale key；目录节点可不带 component。DTO 中不写 `() => import(...)`、`$t(...)`、组件对象、函数、token 或账号凭据。前端 `.vue` 文件仍位于 `src/views/` 并随应用构建，数据库不存 Vue 源码或远程可执行代码。映射实现与运行时校验见 [RBAC 指南](routing-rbac.md)。TypeScript 类型本身不会校验接口 JSON。

业务定义的完整例子见 RBAC 指南。创建该例中的 `orders.ts` 后，汇总入口为：

```ts
// src/router/dynamic/index.ts
import orders from "./modules/orders";
import type { DynamicRouteDto } from "./types";

// 这是开发用的完整资源目录，不是任意账号已被授权的菜单。
export const dynamicRouteCatalog: DynamicRouteDto[] = [...orders];
```

开发 Mock 端点单独导入一次 `dynamicRouteCatalog`，按模拟会话、账号状态及角色/资源授权生成返回树，再用现有 `{ code, message, data }` 包络返回。本模板端点当前在 `mock/auth.fake.ts`；如拆为专用端点文件，应移走旧的同 URL 定义，只保留一个处理器。现有 Mock 不代表已经实现这些状态过滤。

生产浏览器入口、页面和 `src/router/index.ts` **不导入 `dynamicRouteCatalog` 作为当前用户菜单**。静态入口只建立基础路由；动态入口始终是 `src/api/routes.ts` → `initRouter()` → 现有映射/注册流程。不能把两份数组拼进 `createRouter`，也不能在每个页面 mounted 时各自注册。这样接后端时替换的是端点实现，不是 UI 的路由来源。

## 3. 纯前端阶段也遵守动态加载链路

1. 创建视图、locale、领域动态定义和汇总入口，检查 `name`、`path` 与基础路由及其他业务无冲突；从静态模块迁移时同步移除原记录。
2. Mock 使用服务端模拟会话确定用户；根据同一份角色、按钮及账号状态夹具返回允许的路由。不要信任浏览器传入的 `roles`/`status` 作为生产授权。至少覆盖允许与拒绝场景，不能只验证超级管理员。
3. 保留已有 `getAsyncRoutes()` 调用和鉴权链路，避免新增“有后端走 HTTP、无后端直接注册全部本地目录”的第二套逻辑。缓存会跳过请求，开发切换夹具时关闭或失效旧缓存。
4. 先完成当前会话动态初始化，再解析深链接并补充兜底 404；初始化失败提供恢复或回登录路径，不能返回本地全量目录兜底。成功 `data: []` 表示该账号没有动态业务，基础页面仍可初始化。
5. 使用当前项目退出/重置入口。退出、账号切换、权限撤销时清理旧动态记录、菜单、标签、页面缓存和路由缓存；处理切换期间旧请求返回的竞态。现有模板实现及尚未实现部分见 RBAC 指南，不将此规范描述为现成能力。

账号状态不是 `meta.roles` 的同义词：拥有角色但被停用、过期或未完成必要步骤的账号，也可能不能进入业务。具体状态枚举、提示文案、HTTP/业务错误码和可访问范围必须来自已确认的后端契约；这些例子不是新增的字段协议。约定需要状态条件却缺少可信状态时，保持未授权/待确认状态，不能默认放行。

需要独立受限状态页时，先确认它是否属于全局会话基础设施及允许进入的条件，再决定是否静态；不能把某个业务页面移进 `remaining.ts` 来解决跳转。Mock 和真实后端都应控制菜单返回，业务 API 另行校验状态与权限。前端 meta、菜单隐藏、按钮禁用只能呈现授权结果。

新增静态状态页必须同时满足：属于全局会话流程；需要在业务菜单尚未加载或被拒绝时可达；只承载状态提示和约定的会话恢复动作，不混入受业务权限保护的内容；可信状态来源及进入/离开条件已确认并由守卫落实。记录判定依据和验收场景，不能仅凭页面叫“账号受限”就归为基础设施。条件未确认时标为待确认，先完成不依赖它的 UI。

## 4. 入库边界与后端交接

每个动态业务随 UI 交付 `docs/backend/route-manifest.md`，记录下表信息。后端已有模型时对齐现有实体；没有模型时交付可序列化种子数据与映射说明，不假设数据库类型、不虚构已执行 SQL。

最小交付形式是在该清单中分别放入资源、操作权限和角色授权关联的 JSON 代码块，无操作或无关联时显式说明空集合及原因。已有后端种子/迁移工具时改用其独立文件，并从清单链接到具体路径。路由资源部分从同一动态目录导出或逐项核对后记录，作为交接快照；角色与状态政策单独注明待确认项，不维护第二份参与前端运行的路由数组。只有 DTO 而没有资源标识、映射与授权关联说明，不算完成交接。

| 数据          | 交接内容                                                                                                              |
| ------------- | --------------------------------------------------------------------------------------------------------------------- |
| 菜单/页面资源 | 稳定资源 ID 或 key、父级、类型（目录/页面）、唯一 name、path、component key、redirect、排序、locale key、可见性、缓存 |
| 操作资源      | 创建/编辑/删除等权限码及所属业务；按钮不是页面路由，不为了权限码创建虚假 URL                                          |
| 授权关联      | 角色与菜单/页面、角色与操作资源的关联；如有租户/组织条件一并明确；账号状态判断规则单独描述                            |
| 映射          | 资源 ID ↔ 路由 name ↔ 组件 key ↔ 页面文件；数据库字段到 DTO 的转换方式                                                |
| 交付状态      | 本地 Mock 已演示 / 后端已对接 / 待后端实现，分别标记；列出验证过的账号场景                                            |

`DynamicRouteDto` 是客户端所需的数据形状，不等于完整数据库表结构。后端从资源目录和授权关联产生**当前会话已获准的子树**，包括隐藏详情；`meta.auths` 若作为按钮授权来源，只返回该用户实际获准的按钮码，不能原样返回资源库全部按钮。叶子角色条件需显式保留；空父目录、不可访问的 redirect 和无授权落点要按契约处理。

从 Mock 切到后端时：导入种子/完成迁移 → 实现会话与状态过滤及 DTO 映射 → 保持 `GET /get-async-routes` 包络（协议变化在 API 层适配）→ 关闭开发 Mock、配置 API 地址 → 用同一 UI 验收允许/拒绝场景。浏览器继续消费接口；本地目录保留为开发夹具或迁移记录，不成为线上授权回退。

## 5. UI 与验收要求

- 页面开发说明必须给出来源清单与后端待办，包含隐藏详情；导航、面包屑、标签和入口按钮均指向已授权的动态记录。入口尚未获准时不渲染可用链接，不能靠跳转失败代替权限体验。
- 分别呈现菜单加载中、获取失败、无业务权限和列表无数据；业务接口返回拒绝时恢复 loading 并给出约定提示，不伪装成功或空列表。拒绝场景使用项目约定的 403/会话处理，未知路径使用 404；后端未返回某页面时不依赖完整本地目录泄露资源存在性。
- 验证普通账号和拒绝/受限状态账号的菜单、直接 URL、刷新、隐藏详情、按钮、退出后返回与账号切换；验证空动态结果、网络/业务失败、重复 name/path、不存在的 component、旧缓存和迟到响应。
- 确认生产构建没有启用开发 Mock 或注册全量本地目录。本模板已限制 Mock 为开发启用，后续改动仍需保持这一边界。
